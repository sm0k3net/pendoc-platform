# Установка и настройка

## Варианты развёртывания

| Вариант | Frontend | Backend |
| --- | --- | --- |
| Локальная разработка | Vite на localhost | Supabase CLI и Docker |
| Небольшая команда или VPS | Статическая сборка за HTTPS-прокси | Отдельный управляемый проект Supabase либо официальный Supabase Docker |
| Контур организации | Статическая сборка через корпоративную точку входа | Официальный Supabase Docker, закрытая БД и хранилище |

## Локальный запуск

1. Установите Node.js 22.12+, npm и Docker. В корне репозитория выполните `npm ci` и `npx supabase@3.3.0 start`.
2. Скопируйте `.env.example` в `.env.local`. Выполните `npx supabase@3.3.0 status` и укажите URL и publishable либо anon key локального контура.
3. В отдельных терминалах запустите `npx supabase@3.3.0 functions serve` и `npm run dev`. Откройте http://localhost:5173.
4. Зарегистрируйте аудитора и подтвердите email через локальный почтовый ящик, адрес которого показывает `supabase status`. Команда `npx supabase@3.3.0 db reset` удаляет локальные данные и повторно применяет миграции. Используйте её для одноразовых стендов.

## Настройка frontend

| Переменная | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | URL шлюза Supabase, доступный из браузера. Для сервера используйте HTTPS. |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный ключ браузера, publishable key или совместимый anon key. |
| `VITE_PUBLIC_ORIGIN` | Адрес frontend без пути, например `https://reports.example.org`. По умолчанию берётся текущий origin. |

Значения Vite попадают в браузерную сборку. Service-role, пароли БД и ключи провайдеров храните на сервере. Соберите проект через `npm run build` и раздавайте каталог `dist/`. Для маршрутов SPA настройте возврат `/index.html`, отдельно настройте выдачу статических ресурсов. В репозитории есть [пример Nginx](../deploy/nginx.conf).

## Управляемый backend

1. Создайте отдельный проект Supabase на PostgreSQL 15 или новее. Включите подтверждение почты и настройте почтовый сервер Auth.
2. Привяжите CLI v3 к этому проекту, затем вызовите `npx supabase@3.3.0 db push --remote`. Проверьте указанный CLI проект и список миграций. Из того же корня разверните функции через `npx supabase@3.3.0 functions deploy`.
3. В Auth задайте Site URL и укажите точные redirect URL frontend для `/auth?type=client` и `/auth`. Используйте настройки JWT из `supabase/config.toml`. Функции, которые отключают проверку JWT на шлюзе, выполняют проверку авторизации в обработчиках.
4. Соберите frontend с публичным адресом шлюза и ключом отдельного проекта. Выполните приёмочную проверку.

Миграции открытой версии рассчитаны на пустую базу. Перенос с исторической схемы SaaS требует отдельного переноса схемы и вложений.

## On-premise и один VPS

1. Соберите инфраструктуру по [официальному руководству Supabase Docker](https://supabase.com/docs/guides/self-hosting/docker). Закрепите версию стека, сгенерируйте ключи и пароли, закройте доступ к Studio, PostgreSQL и внутренним портам. Настройте TLS, публичный адрес API и Site URL.
2. На доверенном хосте примените миграции в порядке версий. Пример команды для отдельной служебной переменной `PENDOC_DATABASE_URL`: `npx supabase@3.3.0 db push --remote="$PENDOC_DATABASE_URL"`. Перенесите каталоги из `supabase/functions/` в volume официального Edge Runtime, сохранив имена. Сохраните существующий маршрутизатор upstream и настройте вызовы функций с параметрами JWT из `supabase/config.toml`. После загрузки перезапустите Edge Runtime.
3. Настройте SMTP Auth и redirect URL. Подключите закрытое объектное хранилище, соберите и опубликуйте frontend. Открывайте исходящий доступ для SMTP и утверждённых провайдеров по необходимости.
4. Выполните приёмку. Для установки на одном VPS храните зашифрованные копии за пределами VPS и проверьте восстановление на другом хосте.

## Опциональные интеграции

| Переменная серверной среды | Назначение |
| --- | --- |
| `RESEND_API_KEY`, `PENDOC_EMAIL_FROM`, `PENDOC_PUBLIC_ORIGIN` | Уведомления о приглашениях и ретесте. Для отправки нужны все три параметра. При выключенном Resend токен можно передать защищённым каналом вручную. Письма для входа использует отдельная SMTP-настройка Supabase Auth. |
| `DEEPSEEK_API_KEY`, `OPENAI_API_KEY` | Анализ отчётов и помощь с текстом. Провайдер может получить содержимое отчёта или находки. Для закрытого контура оставьте параметры пустыми, пока передача данных не согласована. |
| `NVD_API_KEY` | Опциональный ключ NVD. Обогащение CVE может обращаться к публичному NVD даже без ключа. |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` | Параметры серверных функций. Их подставляет Supabase или доверенный Edge Runtime. |

Локально используйте отдельный игнорируемый env-файл для `functions serve --env-file`. В управляемом проекте используйте Supabase secrets, в Docker — окружение Edge Runtime.

## Приёмка и эксплуатация

- Зарегистрируйте аудитора, подтвердите email, создайте клиента и проект. Импортируйте отчёт поддерживаемого формата, добавьте закрытое вложение, сформируйте отчёт и архив.
- В **Client Access** пригласите второй email. Передайте токен защищённым способом. Клиент вводит адрес и токен, затем открывает письмо для входа в том же браузере. При повторном входе используется только email.
- Проверьте, что черновик остаётся у аудитора. Опубликуйте выбранный отчёт, запросите ретест через клиентский интерфейс, затем отзовите назначение и проверьте ответ при новой попытке чтения из старой клиентской сессии. Скачанную копию отозвать невозможно.
- Резервируйте базу, объекты и конфигурацию. Проверьте восстановление в отдельной среде и повторите основные сценарии входа, отчёта и доступа к файлам.
